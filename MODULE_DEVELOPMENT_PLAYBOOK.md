# VAT-MSA Module Development Playbook

Status: working guidance for engineering. Not an architecture deliverable, not a governance artifact, not a commissioning approval. It translates the current-state assessment (`09-assessments/`), the implementation matrix (`ARCHITECTURE_IMPLEMENTATION_MATRIX.md`) and the domain catalogue (`08-enterprise-architecture/11-domain-capability-catalog.md`) into a sequenced, module-by-module build plan.

Last synchronised against: `ARCHITECTURE_IMPLEMENTATION_MATRIX.md` (2026-08-23) and `09-assessments/CURRENT STATE ASSESSMENT.md`. Re-check those two files before starting any module — this playbook describes *how* to build, not the live status; the matrix is the source of truth for *what's already done*.

## How to use this document

1. Pick **one module**. Read its section fully before writing code.
2. Each module is broken into **phases** (A, B, C…). Work phases in order within the module — later phases assume earlier ones exist. Each phase carries a relative size tag: **S** (days), **M** (roughly a sprint), **L** (multiple sprints) — relative to each other, not a calendar promise.
3. Cross-check the **data model anchors** listed per module against `08-enterprise-architecture/11-domain-capability-catalog.md` for the authoritative command/query/event/API contract — this playbook summarises them, the catalogue is canonical.
4. Check the module's current maturity label in `ARCHITECTURE_IMPLEMENTATION_MATRIX.md` (`VERIFIED PILOT` / `CONTROLLED FOUNDATION` / `DISABLED PENDING AUTHORITY` / `ARCHITECTURE ONLY`) — that tells you whether a phase is hardening, building out, or stubbing.
5. Each task should land as its own reviewable PR with its own migration (follow the existing `0000`…`0019` numbered-migration pattern) and its own tests.
6. Before merging, run the full release gate (lint, typecheck, `pnpm security:ci`, build) — the same gate already evidenced in the implementation matrix. A phase isn't done because it compiles; it's done because it clears the gate and the module's Definition of Done.
7. Update `ARCHITECTURE_IMPLEMENTATION_MATRIX.md` when a module's maturity label actually changes. Do not let status drift from reality — that drift is exactly what the `09-assessments/` audits had to catch and correct.

## Non-negotiable ground rules (apply to every module)

- **Fail closed on unconfirmed authority.** Mirror the existing pattern used for tax-rule binding (rejects unless an approved rule exists) and production signing (throws without an approved signer). Any new capability touching money, tax liability, or identity must refuse to act, not assume, whenever it depends on something not yet confirmed (an ITAS contract, a legal rule, a production key).
- **Never quietly enable a disabled production capability.** ITAS federation, payment settlement, and HSM/KMS signing stay disabled until the corresponding entry in `06-delivery/phase0-production-readiness-evidence-backlog.md` (PR-001–013) is closed with a real signature — not a passing local test. Build against typed adapters and mocks so the *code* is ready the day the *authority* arrives.
- **One canonical taxpayer/organisation identity.** No module may create a parallel identity concept, a shadow buyer/seller account, or a bypass of the canonical taxpayer record. Buyer and Seller are transaction capabilities, never separate accounts (ADR-001/ADR-002).
- **Statutory records are immutable.** Corrections are adjustment/reversal/credit-note/debit-note records, never overwrites or deletes.
- **Every phase ships tests before merge.** Minimum bar per `06-delivery/testing-strategy.md`: unit, security/policy, and integration tests for the module's own API boundary. Domains classified `RESTRICTED_TAX`, `RESTRICTED_RISK` or `RESTRICTED_IDENTITY` in the catalogue additionally need authorization-negative tests (prove the wrong role/scope is rejected, not just that the right one succeeds).
- **RBAC/ABAC on every command and query.** Every command carries actor, organisation/taxpayer scope, purpose and correlation ID; every query carries policy-derived predicates and bounded pagination — repo-wide rule (`11-domain-capability-catalog.md`, "Security rules common to every domain"), not a per-module option.
- **Small increments.** One capability (one command, one query, or one event) per PR wherever practical.

## Module sequencing

```
1. Identity, Taxpayer & Organisation Foundation
2. Tax Invoicing & VAT Engine
3. Reconciliation & Returns
4. Audit & Risk
5. Commercial Operations            ← parallelisable with 3–4, low coupling
6. Documents, Communication & Notifications
7. Reporting & Analytics / BI
8. Platform Administration, Security & Workflow   ← cross-cutting, start early, finish late
9. Refunds & Payments               ← gated on external payment authority
10. External Integrations (ITAS / SaaS / Developer Platform)  ← gated on external contracts
```

Modules 8–10 have components you can and should start early (platform/security scaffolding, the ITAS adapter *interface*) even though production activation is externally gated. "Build the adapter, stub the authority" is the standing pattern for both.

## Module 1 — Identity, Taxpayer & Organisation Foundation

**Domains:** Identity, Taxpayer, Organisation, User Management, Buyer/Seller capability, Licensing & Entitlements, Organisation Administration, Organisation Authorization, Access Governance, Workspace & Navigation.
**Depends on:** nothing — this is the foundation. **Unlocks:** every other module.
**Maturity today:** `CONTROLLED FOUNDATION` (Identity — see Phase A decision below), `VERIFIED PILOT` (Taxpayer, Organisation, User Management, Buyer/Seller, Licensing & Entitlements, Organisation Administration, Organisation Authorization, Workspace & Navigation).

**Two decisions recorded 2026-08-25** (were open questions; both now settled and built against):
1. **Identity/Session model:** this system has no session it actually controls — no cookie, no JWT; the ChatGPT/OpenAI platform is the real authentication authority, and `getCurrentUser()` just trusts a fresh header per request. Building a literal `Session`/`CredentialMetadata` table would be synthetic and could make `RevokeSession` look like it does something it can't fully back. **Decision: "session" = the `identity_link`.** `RevokeSession` revokes the identity_link (a real, verifiable effect — `getCurrentUser()`'s join requires `status='ACTIVE'`, so a revoked link stops authenticating on its very next request). `Session`/`CredentialMetadata` tables stay deferred until a real credential-issuing mechanism exists (ITAS confirmed, or the standalone `VAT_MSA_STANDALONE` identity provider — seeded but `PENDING`/`REQUIRES_SECURITY_DECISION` — is activated).
2. **Self-service provisioning:** there is still no path for a brand-new person (no existing `app_users` row) to get their first account — `getCurrentUser()` deliberately throws rather than auto-provisioning. **Decision: explicit invite-and-claim**, generalizing the `inviteEmployee`/`activateEmployee` pattern beyond employees. **Built**: `POST /api/v1/organisations/:id/invitations` (org admin invites an email to a taxpayer-side role; returns a single-use claim token since this repo has no outbound email integration to deliver it) and `POST /api/v1/invitations/claim` (the invitee, authenticated only by the platform identity — no `app_users` row required to reach this one route — redeems the token; creates their `app_users` row, identity link and membership atomically, with an email-match check as defense in depth against a leaked token).

**Data model anchors:** `Provider`, `IdentityLink`, ~~`Session`, `CredentialMetadata`~~ (deferred, see decision above) · `TotpCredential` (`mfa_totp_credentials`), `StepUpEvent` (`step_up_events`, added 2026-08-27, see Phase A below) · `Taxpayer`, `VATRegistration`, `TIN`, `IdentifierVersion` · `Organisation` aggregate, `Branch`, `Capability` · `User`, `Membership`, `Invitation`, `LifecycleCase` · `OrganisationCapability`, `TransactionRole` · `LicensePlan`, `Subscription`, `OrganisationLicense`, `Entitlement`, `LicenseUsage` · `Employee`, `Position`, `Department`, `BusinessUnit`, `OrganisationAdministrator` · `OrganisationRole`, `RolePermission`, `UserRole`, `UserCapability` · `AccessRequest`, `AccessReview`, `AccessCertification` · `NavigationWorkspace`, `NavigationFolder`, `NavigationItem`, `NavigationPermission`.

### Phase A — Canonical identity & session (M)
- [x] `Provider`, `IdentityLink` model (`Session`/`CredentialMetadata` deferred — see decision above).
- [x] `LinkIdentity` (`POST /api/v1/identity/links`, admin-only, fails closed against any provider not `ACTIVE`+`CONFIGURED`) / `RevokeSession` (`POST /api/v1/identity/links/:id/revocation`, = revoke the identity_link). A 2026-08-27 security audit (`SECURITY_GAP_ASSESSMENT.md`) found both performed no tenant-scope check on the *target* user/link at all — since `administration:manage` is tenant-grantable (TAXPAYER_OWNER/TAXPAYER_ADMIN hold it for ordinary org administration), a tenant admin could link a platform identity they control to any `app_users` row, including a national-scope account, and authenticate as it; or revoke any other user's session. Fixed the same day: a non-national actor's target must now share their own `taxpayer_id`; a genuinely national-scope actor is unrestricted, matching `resolveTaxpayer`'s own established pattern. Proven in `tests/routes/security-identity-link-scope.test.ts`.
- [x] `ResolveIdentity` (`GET /api/v1/identity/links`) / `GetAssurance` (`GET /api/v1/identity/assurance`, combines identity-link assurance with a real server-verified step-up freshness check) queries. The same 2026-08-27 audit found step-up itself (`requireStepUp`) trusted two client-supplied request headers verbatim, with zero server-side backing — no application code anywhere ever set them on a genuine step-up event, only test fixtures did, so all ~28 "step-up gated" commands across every module were effectively ungated. Fixed the same day with a real, standards-compliant RFC 6238 TOTP implementation (`lib/domain/mfa.ts`, pure Web Crypto — no external MFA provider needed): `EnrollTotp`/`VerifyTotpEnrollment` (`POST /api/v1/identity/mfa/totp[/verification]`) establish a credential, `ConfirmStepUp` (`POST /api/v1/identity/step-up`) verifies a fresh code and writes a real `step_up_events` row (anti-replay via a persisted HOTP counter), and `requireStepUp` now checks that row. Proven in `tests/mfa-domain.test.ts` and `tests/routes/security-mfa-step-up.test.ts`.

### Phase B — Taxpayer & organisation core (M)
- [x] `SuspendTaxpayer` (`POST /api/v1/taxpayers/:id/suspension`, idempotent, immediately enforced via existing `vat_status='ACTIVE'` filters).
- [x] `IdentifierVersion`/effective-dating on `taxpayer_identifiers` (`version`, `effective_from`, `effective_to`, `previous_version_id` columns). `POST /api/v1/taxpayers/:id/identifiers/:identifierId/correction` supersedes the current VAT_NUMBER/TIN row rather than overwriting it, and keeps the denormalized `taxpayers.vat_number`/`tin` columns in sync so the correction actually takes effect on counterparty resolution. `GetOrganisation` now surfaces the full version history per identifier.
- [x] `VerifyIdentifiers` standalone (`POST /api/v1/taxpayers/:id/identifiers/verification`) — re-triggerable at any time after registration (previously verification only ever happened once, at intake). Calls the same `ItasIdentityPort` registration intake uses; today that always fails closed since ITAS is unconfigured, and the command honestly reports `AWAITING_PROVIDER_CONTRACT` rather than faking success.
- [x] `ActivateOrganisation`, `EnableCapability` (both via `POST /api/v1/registration-applications/:id/decision`, which also creates the head-office branch and owner membership) — `GetOrganisation` pre-existing, `ListBranches` + branch create/update now standalone (`GET`/`POST /api/v1/organisations/:id/branches`, `PATCH .../branches/:branchId`).

### Phase C — Users, roles & buyer/seller capability (M)
- [x] `ProvisionUser` (invite-and-claim, see decision above). `SuspendUser` (`POST /api/v1/users/:id/suspension`) and its reverse (`POST /api/v1/users/:id/reactivation`) are now standalone — a reversible lockout distinct from `terminateEmployee`'s one-way offboarding, which still also suspends `app_users` as one part of a larger irreversible action.
- [x] `AssignMembership` (`POST /api/v1/organisations/:id/memberships`, restricted to TAXPAYER_* roles — a deliberate privilege-escalation guard).
- [x] `GetUserAccess` (`GET /api/v1/me/access`) — the full effective RBAC+ABAC predicate set, computed live.
- [x] `CreateRole`/`AssignPermission` pre-existing; `GrantCapability` now standalone (`GET`/`POST /api/v1/organisations/capabilities`, upserts, requires the org to already hold the capability).
- [x] `ClassifyTransaction` (`GET /api/v1/counterparties/classification`) and `GetAvailablePortals` (`GET /api/v1/portals` — the underlying logic already existed, gating every portal page; this exposed it as its own endpoint).

### Phase D — Licensing, administration & access governance (L)
- [x] `Activate`/`Suspend`/`Renew` (`POST /api/v1/licensing/state`) and `Upgrade` (`POST /api/v1/licensing/upgrade`, a distinct plan-change operation, not a state transition); standalone `GetEntitlements`/`GetUsage` (`GET /api/v1/licensing/entitlements`, `GET /api/v1/licensing/usage`).
- [x] `AppointAdministrator` (`GET`/`POST /api/v1/organisations/administrators`) and employee `INVITED → ACTIVE` (`POST /api/v1/organisations/employees/:id/activation`, also converts the USER_SEATS licence reservation into usage).
- [x] `AccessRequest`/`AccessReview`/`AccessCertification` request/approve/certify already existed; standalone `RevokeAccess` (`POST /api/v1/access-grants/revocation` — revokes one active role or capability grant on demand) and `Offboard` (`POST /api/v1/organisations/offboarding` — revokes every active grant plus the membership itself, immediately) are now distinct commands, decoupled from `certifyQuarterlyAccess`'s review-gated bulk revoke and from `terminateEmployee`'s licence/employment-coupled offboarding.

### Phase E — Workspace projection & hardening (S)
- [x] `GetWorkspace` pre-existing; `GetChildren` (`GET /api/v1/navigation/children`, properly traverses nested `parent_folder_id`), `GetActions` (`GET /api/v1/navigation/actions`, explainable single-item access check) and `SavePreference` (`POST /api/v1/navigation/preferences`, upserts) now built. `NavigationPermission`/`navigation_permissions` remains unwired — flagged, not fixed.
- [x] Negative-test suite: `tests/routes/module-1-access-control.test.ts` — cross-organisation access, cross-role access, expired step-up and insufficient assurance level are now provably rejected through real route handlers, backed by a real SQLite engine (`tests/support/fake-d1.ts`, over Node's built-in `node:sqlite`) via test-only stand-ins for `cloudflare:workers` and `next/headers` (`tests/fakes/`) — both only resolve inside their real runtimes, which is why no route/repository code could be tested end-to-end before this. `vitest.config.ts` aliases the three specifiers to these fakes; pure-domain tests are unaffected since they never import anything that reaches them.

**Watch-outs:**
- `GetUserAccess` must never be a cached/stale snapshot — every module trusts it live.
- Buyer/Seller capability is a flag on the one `Organisation`, never a second account row.
- Licensing/Entitlement gates features; it must never be able to gate statutory correctness (a suspended licence can't be the reason a VAT calculation comes out wrong).

**Definition of done:** a user can be provisioned, assigned a role scoped to one organisation, and every subsequent API call in the system can resolve "who is this, what organisation, what capability, what assurance level" from this module alone — with negative tests proving cross-organisation and cross-role access is rejected.

## Module 2 — Tax Invoicing & VAT Engine

**Domains:** Tax Invoice, VAT (rules/calculation), Transaction (immutable ledger).
**Depends on:** Module 1 (resolved identity/organisation/branch). **Unlocks:** Module 3 (returns need certified invoices/transactions), Module 5 (quotation conversion), Module 9 (refund freezes invoices/transactions).
**Maturity today:** `VERIFIED PILOT` (Tax invoice, VAT) — this line was originally written before any Module 2 coding happened this cycle and was aspirational, not a record of reality: a 2026-08-25 code assessment found Phase A entirely unbuilt (the tax rate was 100% client-supplied, only arithmetic-checked) and Phases B-D built as one monolithic `submitInvoice` rather than as the named standalone commands below. All five phases (A-E) are now genuinely closed as of this cycle's work — see each phase below for what was actually built versus simplified/merged from the original aspiration, and the Architecture Implementation Matrix's domain #9/#10 rows for the governance-level items still required before national production.

**Data model anchors:** `TaxInvoice` aggregate, `InvoiceItem`, `Sequence`, `Reservation`, `Certificate` · `VATRule`, `VATCalculation`, `EligibilityDecision` · `VATTransaction` aggregate, `Adjustment`, `Reversal`.

### Phase A — Rule engine (M)
- [x] `VATRule` with effective-dating (`vat_rules` table, `UNIQUE(tax_category,country,version)`, `effective_from`/`effective_to`) and `ProposeVatRule`/`ApproveVatRule` (`POST /api/v1/vat-rules`, `POST /api/v1/vat-rules/:id/approval` — segregation of duties, self-approval denied). Deployment-bootstrapped with Namibia's real statutory rates (15% standard; 0% zero-rated/exempt/outside-scope; reverse-charge at the standard rate); `OTHER` deliberately has no approved rule.
- [x] `EvaluateVAT` (`GET /api/v1/vat-rules/evaluate?tax_category=&date=`, standalone dry-run) and `ExplainCalculation` (`GET /api/v1/invoices/:id/vat-explanation`, per-line traceability to the exact approved rule version). Fails closed: `submitInvoice` now rejects any line whose category has no approved rule, or whose supplied rate doesn't match the resolved one — previously the client-supplied rate was trusted outright.
- `VATCalculation`/`EligibilityDecision` as named types were not built separately — the calculation itself still lives in `calculateAndValidateInvoice` (arithmetic) plus the new rule-resolution check (statutory correctness); this is a reasonable simplification, not a gap, since nothing else needs those as standalone records.

### Phase B — Invoice lifecycle (L)
- [x] `TaxInvoice` aggregate (`invoices` + `invoice_lines`), `Certificate` (`certificates`). `Submit`/`Certify` exist as one atomic command (`submitInvoice`, `POST /api/v1/invoices`) rather than two separate steps — reasonable, since nothing in this codebase needs a certifiable-but-uncertified invoice state. `Get`/`VerifyInvoice` exist (`GET /api/v1/invoices/:id`, `GET /api/v1/verify/:token`).
- [x] `invoice_number` is now unique per supplier (`UNIQUE(supplier_taxpayer_id, invoice_number)` on `invoices`, plus an explicit pre-check in `submitInvoice` for a clear `RepositoryConflictError` rather than a raw constraint failure). No full `Sequence`/`Reservation` *allocation* aggregate was built (that's a materially bigger feature — pre-allocating number ranges for offline/high-volume devices — and the matrix's required-closure column already treats it as a separate, governance-dependent item); this closes the correctness-critical half (collisions are now impossible), not the allocation half.
- [x] `Cancel` (`CancelInvoice`, `POST /api/v1/invoices/:id/cancellation`) now exists. Deliberately narrow and officer-only, not self-service by the submitting taxpayer (`invoices:cancel`, held only by PILOT_ADMIN/NAMRA_SYSTEM_ADMIN) — a taxpayer that made an error must go through a credit/debit note, the same as anyone else; only NamRA can void an invoice outright. Restricted to original tax invoices with no active correction against them (an invoice already in a correction lineage must be resolved through further corrections, not voided out from under them) — this design choice was made as an engineering judgment call rather than escalated as a blocking question, since it's additive and adjustable, unlike Module 1's session/provisioning decisions. Reverses ledger/return effect the same way a credit note does (new flipped-direction rows, never mutating existing ones); idempotent.
- [x] `VerifyInvoice`'s public output now includes correction and cancellation lineage — see Phase C.

### Phase C — Correction lineage (M)
- [x] Credit/debit note handling is real and correctly implemented (inlined in `submitInvoice`'s `isCorrection` branch, not standalone `CreateCredit`/`CreateDebit` commands — a reasonable simplification given how tightly coupled correction validation is to the same submission pipeline). Original-invoice matching, currency/date/customer-identity checks and cumulative-credit-cap validation are real; the original invoice row is never mutated.
- [x] Linkage is now surfaced in `VerifyInvoice`'s public output (`GET /api/v1/verify/:token`): whether the invoice is itself a correction (and what it corrects), and the list of corrections against it (type, status, masked invoice number, amount, date) — deliberately excludes `reason`/`reason_code` text, kept authenticated-only in `GET /api/v1/invoices/:id`, since this is an unauthenticated public endpoint. The invoice's own `status` (including `CANCELLED`) is now public too.

### Phase D — Immutable ledger (M)
- [x] `VATTransaction` now has a real table (`vat_transactions`: id = the `transaction_id` already tagged onto `ledger_entries`, invoice_id, taxpayer_id, transaction_type [CERTIFICATION/CORRECTION/CANCELLATION], reference_transaction_id, created_at) — previously only an implicit UUID grouping key, with no record of its own. `PostTransaction` and `Reverse` are not separate API routes (there's no standalone use case — ledger posting only ever happens as a side effect of certifying or cancelling an invoice) but are real, distinct code paths: `submitInvoice` posts a CERTIFICATION or CORRECTION row, `cancelInvoice` posts a CANCELLATION row linked back via `reference_transaction_id` to the certification it reverses. No standalone `Adjust`/`Adjustment` was built — nothing in this codebase has a use case for adjusting a transaction's amount without it being either a correction (a new invoice) or a cancellation (a full reversal); a partial in-place adjustment would violate the same immutability principle these already respect.
- [x] `GetTransactionTimeline` (`GET /api/v1/invoices/:id/transaction-timeline`) reads back the complete chronological narrative for one invoice's lineage — its certification, every correction, and its cancellation if any — each event carrying the ledger postings it actually made. Accepts any invoice id within the lineage (the true original or one of its corrections) and always resolves to the same root.
- Note: `lib/data/vat-lifecycle-repository.ts` looks related by name but is VAT-*return*-period adjustment logic (a different domain, likely Module 3), not this ledger.

### Phase E — Hardening (M)
- [x] Idempotency under concurrent retries. The SELECT-then-INSERT check was not itself atomic; a race that lost was previously an unhandled `UNIQUE constraint failed` error surfacing as a raw 500. `submitInvoice` now catches a constraint violation from `db.batch(statements)`, re-checks `idempotency_records` for a matching row, and returns that prior result if the request hash matches (a genuine race on the same submission) — or the existing `RepositoryConflictError` if it doesn't (a different payload reusing the key, or a different document colliding under a different key). `tests/routes/module-2-invoice-hardening.test.ts` fires the identical request twice via `Promise.all` (a real interleaved-async race, not a sequential call) and asserts exactly one invoice row results.
- [x] The unidentified-buyer guarantee (this phase's flagged P0) was already correctly implemented (`repository.ts`: the `INPUT_VAT` ledger insert and customer-side return update only happen inside `if (customer)`) but had zero test coverage. `tests/routes/module-2-invoice-hardening.test.ts` now asserts directly against `ledger_entries` for both the suppressed case (unresolved buyer → zero `INPUT_VAT` rows) and the posted case (an active BUYER-capable organisation → exactly one).

**Watch-outs:**
- `ExplainCalculation`'s fail-closed behaviour is load-bearing for the whole system's statutory defensibility — don't let a future refactor quietly add a fallback rate.
- Correction records and reversal records look similar; keep their semantics (supersede vs. cancel) distinct in the data model, not just in naming.

**Definition of done:** invoice → certified → VAT-calculated → transaction-posted → correction-capable, fully idempotent under concurrency, fully explainable to a specific rule version, with the unidentified-buyer guarantee under test. All five phases now meet this. Remaining work is governance-level, not functional: legal invoice particulars, an official numbering *allocation* system for offline/high-volume devices, NamRA sign-off on the cancellation eligibility policy, HSM signature profile, golden VAT-rate cases and a formal rate-change rollback runbook — see the Architecture Implementation Matrix's domain #9/#10 "Required closure" columns.

## Module 3 — Reconciliation & Returns

**Domains:** Reconciliation, VAT Return, Compliance.
**Depends on:** Module 2 (invoices/transactions to match), Module 1 (officer identity for assignment). **Unlocks:** Module 9 (refund freezes a submitted return), Module 4 (exceptions can seed audit referrals).
**Maturity today:** `VERIFIED PILOT` (VAT Return), `CONTROLLED FOUNDATION` (Reconciliation, Compliance) — a 2026-08-25 code assessment found this roughly accurate for VAT Return (real, solid work: `generateVatReturn`, maker-checker `decideVatApproval`, `submitVatReturn` correctly stopping at the ITAS boundary) but confirmed Reconciliation is much thinner than its data-model anchors suggest — see Phase A/B below.

**Data model anchors:** `Match`, `Exception`, `Resolution` · `VATPeriod` aggregate, `VATReturn`, `ReturnLine`, `Submission` · `ComplianceProfile`, `Obligation`, `Deadline`, `Action`.

### Phase A — Matching engine (L)
- [x] `Match` is real: `reconciliation_matches` (previously seed-only, never written by application code) is now written by `RunMatch` (`runMatch`, `POST /api/v1/invoices/:id/match`) — an independent verification pass that re-derives what an invoice's ledger postings *should* be from its own declared figures/status and compares against what was actually posted (`evaluateInvoiceMatch` in `lib/domain/reconciliation.ts`: the invoice's own OUTPUT_VAT posting, its INPUT_VAT posting if it has an identified buyer (also re-verifying Module 2's unidentified-buyer guarantee as an ongoing control, not just a one-time code review), and its reversing OUTPUT_VAT posting if cancelled). `RunMatch` is deliberately invoice-scoped, not a period-wide sweep or a literal scheduled/event-driven job — this Workers deployment has no cron/queue infrastructure configured yet, so "scheduled/event-driven" is a documented, deliberate gap rather than faked; this is the correct per-invoice building block such a job would call. `Exception` was already real (`reconciliation_exceptions`, written on submission for RISK_REVIEW/UNREGISTERED_BUYER); `RunMatch` now also raises one for a `LEDGER_MISMATCH`. No standalone `Resolution` table was built — resolution is a status/column change on the exception itself (`resolved_by`/`resolution_notes`/`resolved_at`), not a separate append-only record; given exceptions are never deleted and every transition is audited, a denormalized resolution on the exception row is simpler and no less auditable than a separate table would be.
- [x] `Assign` (`assignException`, `POST /api/v1/exceptions/:id/assignment`) and `ResolveException` (`resolveException`, `POST /api/v1/exceptions/:id/resolution`, idempotent) now exist — `reconciliation_exceptions` gained `assigned_officer_id`, `resolved_by` and `resolution_notes` columns. `Open` was already the exception's initial status from submission; no separate `Open` command was needed. No ageing concept was built (that belongs to Phase B's `GetWorkQueue`, a filterable query, not a mutation command).
- [x] `RunMatch` idempotency: backed by `reconciliation_matches`' own `UNIQUE(invoice_id, taxpayer_id)` constraint — a retry against an already-matched invoice returns the existing match rather than re-evaluating or duplicating.

### Phase B — Work queue (M)
- [x] `GetWorkQueue` (`getWorkQueue`, `GET /api/v1/exceptions`) now exists: real `status`/`severity`/`assigned_officer_id`/`unassigned_only`/`min_age_days`/`max_age_days` predicates, plus bounded `limit`/`offset` pagination with a genuine `totalCount` — designed in from the start (two covering indexes, `idx_reconciliation_exceptions_queue` and `idx_reconciliation_exceptions_officer`, added alongside the query itself) per this module's own watch-out note, not retrofitted after a performance complaint. Age is computed live (`julianday('now') - julianday(created_at)`), not stored, so it's always current. Tenant-scoped the same way the pre-existing `listExceptions` was (kept as-is for its one existing caller, `app/reconciliation/page.tsx`, rather than migrated — no behavioural need to touch it).

### Phase C — Return assembly (M)
- [x] `VATPeriod`/`VATReturn`/`ReturnLine`/`Submission` exist and are solid (`lib/data/vat-lifecycle-repository.ts`, routed via `app/api/v1/vat-periods*`, `app/api/v1/vat-returns/*`): `generateVatReturn` computes from real ledger/certificate data with status filtering and approved adjustments, versioned and idempotent; `decideVatApproval` is real maker-checker (self-approval denied); `submitVatReturn` correctly stops at the ITAS boundary with an explicit `BLOCKED_CONFIGURATION` status and reason, never a silent success.
- [ ] **No explicit `OpenPeriod`/`ClosePeriod` commands exist.** `vat_periods` rows are seed-only; the period only becomes `LOCKED` as an implicit side effect of return approval, not its own command. Publishing is maker-checker only in the loose sense every other command here uses (self-publish is allowed — publishing isn't a second human sign-off on someone else's work, it's confirming your own report is still accurate); a run can only be published once (idempotent-guarded, same pattern as every other command in this file). A published run remains exportable — Phase B's `RequestExport` was updated to accept `COMPLETED_INLINE` or `PUBLISHED`, since publishing an official figure should never retroactively block distributing it.
- [x] **Deliberately scoped down, documented as a real gap, not silently dropped:** the reconciliation re-derives from the *same* source tables the report's own query reads — it catches drift (data that changed after the run) but not a corrupted or wrong query (since both the original run and the reconciliation check share the one `computeReportResult` implementation). ## Module 9 — Refunds & Payments

**Domains:** Payment, plus the refund workflow described in `08-enterprise-architecture/22-audit-refund-reporting.md` (not a separate catalogue domain — model as a state machine owned jointly by VAT Return and Payment).
**Depends on:** Module 2 (frozen invoices/transactions), Module 3 (frozen return), Module 4 (`Risk.EvaluateRisk` reuse). **Unlocks:** nothing further — mostly terminal.
**Maturity today:** the claim state machine, freeze/checks, risk routing and maker-checker (Phases A–C) are complete and tested. Payment itself remains explicitly `DISABLED PENDING AUTHORITY` (Phase D: typed connector interface and DB-backed guard built and tested; no live payment instruction is, or can be, issued). Note: Phase C's maker-checker deliberately reads `refund_claim_transitions` directly rather than Module 8's Workflow engine (see Phase C's own writeup for why) — Module 8 is not actually a dependency of this module's built state.

**Data model anchors:** `Payment`, `Allocation`, `SettlementReference` · refund-claim aggregate (state machine spanning `VATReturn` + `Payment`).

### Phase A — Claim state machine (L) — DONE 2026-08-27
- [x] Full state machine, mirroring Module 4's `CASE_TRANSITIONS`/`transitionCase` pattern exactly (`REFUND_CLAIM_TRANSITIONS` adjacency map + `assertRefundClaimTransition` in `lib/domain/compliance.ts`, one shared transition path per actor type in `lib/data/compliance-repository.ts`): `BLOCKED_RETURN_NOT_FILED --RECHECK_ELIGIBILITY--> RECEIVED --APPROVE--> RISK_REVIEW --APPROVE--> OFFICER_REVIEW --APPROVE--> PAYMENT_AUTHORISATION --APPROVE--> PAYMENT_PENDING`, each of `RECEIVED`/`RISK_REVIEW`/`OFFICER_REVIEW`/`PAYMENT_AUTHORISATION` also reachable to `REJECTED` or a pausable `EVIDENCE_REQUESTED`/`ON_HOLD` state, and `REJECTED --DISPUTE--> DISPUTED --RESOLVE_DISPUTE_OVERTURN--> RISK_REVIEW` / `--RESOLVE_DISPUTE_UPHOLD--> CLOSED`. Deliberate deviations from the playbook's named states, each a considered simplification rather than an oversight: no separate `Validation` state — the `BLOCKED_RETURN_NOT_FILED`/`RECHECK_ELIGIBILITY` gate already built by Module 3 Phase D covers the one real validation this codebase can perform pre-review (return must be `FILED`); no separate `Approved` bucket — each stage's `APPROVE` action names its own next stage directly, which is more precise than a generic status a reader would have to cross-reference against "which stage was this approval for"; no separate persisted `Offset` state — the debt offset is computed live (a `SUM(amount_cents)` query against `tax_obligations` for the taxpayer's `PENDING` obligations, queried fresh at `PAYMENT_AUTHORISATION`'s `APPROVE`, never cached) and recorded as `offset_amount_cents`/`net_payable_cents` columns on the same transition, folded into that one transition's single audit/outbox row per the "one audit row per command" hash-chain-linearity constraint documented on `transitionCase`; `Paid`/`Failed`/`Reversed` deliberately not built — those require an actual payment instruction, which is explicitly Phase D's job and explicitly out of scope while Payment stays `DISABLED PENDING AUTHORITY`. `RESUME` (from either pause state) resolves its target dynamically from a `resume_status` column, the same `to: null` convention Module 4 uses for its own `SUSPEND`/`RESUME`. The one taxpayer-initiated action (`DISPUTE`) is a separate function (`disputeRefund`) from the officer-only path (`transitionRefundClaim`) rather than one function with internal actor-branching, since the two authorisation shapes don't overlap; both reuse the same domain-layer adjacency map, since it only encodes structural status+action legality, independent of who may call it. `transitionRefundClaim` keeps refunds' own original simpler self-review hard-denial (no `cases:override-sod`-style override path, unlike Module 4). Not started: reusing Module 4's real `Risk.EvaluateRisk` for routing, and Module 8 Workflow-engine maker-checker — both explicitly Phase C's job, confirmed still untouched by refund code.
- [x] Every state transition under test — `tests/routes/module-9-refund-claim-lifecycle.test.ts` proves the full happy path to `PAYMENT_PENDING` with a real live-computed debt offset, `REJECT → DISPUTE → RESOLVE_DISPUTE_OVERTURN` and `→ RESOLVE_DISPUTE_UPHOLD`, dispute restricted to the original requester, `HOLD`/`REQUEST_INFORMATION` pause+dynamic `RESUME` from two different stages, `RECHECK_ELIGIBILITY`'s live re-check (blocked while the return is still a live `DRAFT`, succeeds once it is genuinely `FILED`), maker-checker self-review denial (checked before transition validity), an out-of-order transition on an already-terminal claim, and permission denial for a non-reviewer actor. `tests/compliance-domain.test.ts` covers the pure adjacency-map validator directly. All run against the real route handlers (`app/api/v1/refunds/...`) end to end, not just the domain layer.

### Phase B — Freeze & integrity checks (M) — DONE 2026-08-27
- [x] Snapshot the submitted return version, invoices, reconciliation state and rule version at claim time — immutable from that point, even if the underlying data later changes. `requestRefund` now calls `buildRefundClaimSnapshot` once, at claim creation, writing `claim_snapshot` (JSON: the return version's own figures/status/hash, the tax rule set's jurisdiction/version/rate, the taxpayer's reconciliation-exception counts, and a tamper-evident hash of the exact invoice id+payload_hash set for the claim's period) and `claim_snapshot_hash` to two new `refund_claims` columns — written once, and never touched again by `transitionRefundClaim`/`disputeRefund` or any other later code path. This is deliberately a *different* kind of freeze than `PAYMENT_AUTHORISATION`'s debt-offset computation (Phase A), which stays intentionally live: the claim's evidentiary basis must never silently drift even if the return is later corrected, but the taxpayer's *current* statutory debt is the financially correct thing to offset against at payment time, not whatever it was when the claim was lodged. Proven with a real drift test: the source return/invoices/reconciliation rows are mutated after freeze, and the claim's snapshot (and its hash) are asserted unchanged.
- [x] Eligibility, duplicate, debt-offset, identity, bank/account-ownership, sanctions, anomaly checks — each its own testable policy with an explainable pass/fail, never a black-box composite score. A new `refund_claim_checks` table (one row per check per claim, persisted by the same `requestRefund` call) holds eight named checks: `ELIGIBILITY_NEGATIVE_NET_POSITION`/`ELIGIBILITY_RETURN_FILED`/`DUPLICATE_CLAIM` formalise gates `requestRefund` already hard-enforces (persisted as inspectable evidence, not new gates — `ELIGIBILITY_RETURN_FILED` genuinely reports `FAIL` for a `BLOCKED_RETURN_NOT_FILED` claim rather than being skipped); `DEBT_OFFSET_PREVIEW` (a live, non-authoritative preview of the taxpayer's current `PENDING` statutory debt) and `ANOMALY_CLAIM_FREQUENCY` (flags a taxpayer's 3rd-or-later refund claim within a trailing 90 days) are genuinely new, small, code-versioned checks in the same fixed-catalogue shape Module 4 Phase A already established for risk rules — both advisory/non-blocking, since acting on them to route or gate a decision is explicitly Phase C's job, not this one's. `IDENTITY_VERIFICATION`/`BANK_ACCOUNT_OWNERSHIP`/`SANCTIONS_SCREENING` are explicitly persisted as `NOT_CONFIGURED` rather than a fabricated `PASS` — no identity/bank/AML screening provider exists anywhere in this codebase, matching this deployment's established honesty convention (the ITAS `UnconfiguredItasIdentityAdapter`, HSM's `DISABLED` `component-hsm` row, Payment's own `DISABLED PENDING AUTHORITY`) of saying so explicitly rather than silently passing a check nothing actually evaluated. A new `GetRefundClaimChecks` read (`GET /api/v1/refunds/:id/checks`, tenant-scoped exactly like `CaseTimeline`) surfaces both the frozen snapshot and the full check battery.

### Phase C — Risk routing & maker-checker (M) — DONE 2026-08-27
- [x] Reuse Module 4's `Risk.EvaluateRisk` — do not fork a second risk engine here. `requestRefund` now reads the taxpayer's own OPEN `risk_indicators` rows — the exact rows Module 4 Phase A's `evaluateRisk` rule catalogue writes — via a new `reuseTaxpayerRiskSignal` read (`lib/data/compliance-repository.ts`), and takes the more severe of that live signal and the pre-existing amount-based tier as the claim's `risk_tier`. No new detection rules, no new scoring logic, no second risk engine — a refund claim never triggers a fresh `EvaluateRisk` run itself (that stays an explicit, national-scope-gated command an officer chooses to run); it only consumes whatever signal already exists on record at claim time, the same way Module 4's own `approveRiskAction` case-escalation path consumes it. Persisted as a new, explainable `RISK_INDICATOR_SIGNAL` check in Phase B's check battery (`FAIL` for an open `HIGH`/`CRITICAL` indicator, `PASS` otherwise), so the reused signal is inspectable evidence, not a hidden multiplier.
- [x] Route by risk tier to configured review lanes. `risk_tier` now has a real behavioural consequence for the first time (previously a cosmetic label with no downstream effect): a `MEDIUM`-tier claim stays on the **standard lane**, where only the final, material approval needs a distinct officer; a `HIGH`/`CRITICAL`-tier claim is routed onto the **enhanced lane**, where every approval in the chain needs a distinct officer from the one immediately before it — proven with a claim elevated to `CRITICAL` purely by a reused risk indicator (not amount), confirming the routing genuinely reads Module 4's signal rather than just the claim's own size.
- [x] Two-distinct-actor maker-checker enforcement for any material outcome. `transitionRefundClaim` now refuses an `APPROVE` when the acting officer is the same actor who performed the *immediately preceding* transition on this claim, enforced universally for the `PAYMENT_AUTHORISATION → PAYMENT_PENDING` step (the fund-releasing outcome, checked regardless of risk tier) and additionally at every step for the enhanced lane. `refund_claim_transitions` (Phase A) already recorded every actor per stage, so this reads directly off that existing log rather than needing new state. Deliberately **not** built on Module 8's Workflow engine: migrating the refund claim state machine onto that generic engine would be a large, cross-module structural change for no functional gain here, since the transitions log already gives this command everything it needs — the same "not this phase's job" reasoning Phase A already applied to the identical question.
- [x] Proven in `tests/routes/module-9-refund-risk-routing.test.ts`: a small claim from a taxpayer with no open risk signal stays `MEDIUM` and allows the same officer to approve two consecutive non-material stages but still requires a distinct officer for the final approval; the identical-amount claim from a taxpayer carrying a pre-existing `OPEN`/`CRITICAL` risk indicator is elevated to `CRITICAL` and refuses the same officer at every stage, not just the last. `tests/routes/module-9-refund-claim-lifecycle.test.ts`'s Phase A happy-path test was updated to alternate two officers across its now-enforced HIGH-tier chain.

### Phase D — Payment connector interface (M — stops at the boundary) — DONE 2026-08-27
- [x] `Payment` (`payment_instructions`), `Allocation`/`SettlementReference` (an allocation is modelled as `payment_instructions.status` moving to `SETTLED` with a `provider_reference`/`settled_at`, not a separate table — one instruction has exactly one settlement in this deployment, so a join table would be structure with no behaviour behind it yet); `RecordPayment`/`AllocatePayment` (`POST /api/v1/refunds/:id/payment`, `POST /api/v1/refunds/:id/payment/allocation`) and `GetOutstanding` (`GET /api/v1/payments/outstanding`, national-scope only — no taxpayer-facing "my outstanding refund" view exists yet, so this doesn't invent one) against a typed `PaymentConnectorPort` (`lib/integrations/payment.ts`: `status`/`recordPayment`/`allocatePayment`), backed by a genuine `SandboxPaymentConnector` mock — deterministic provider reference and response hash, real `INITIATED`→`SETTLED` status transitions — not a bare stub. `lib/domain/payment.ts` validates command input (never an amount from the client — the amount is always the claim's own `net_payable_cents`, computed server-side at `PAYMENT_AUTHORISATION`) and masks any beneficiary reference before it ever reaches storage. `lib/data/payment-repository.ts` (`recordRefundPayment`/`allocateRefundPayment`/`getOutstandingRefunds`) is a new, separate repository from `compliance-repository.ts` — Payment is its own catalogue domain per the playbook's Module 9 "Domains" line, not a sub-resource of the refund claim state machine; `recordRefundPayment` only ever *reads* `refund_claims.status` (must already be `PAYMENT_PENDING`) and never writes to it or to `refund_claim_transitions` — Phase A/C's state machine stays exactly as it was left, untouched.
- [x] A real, DB-backed environment guard, not documentation. `SandboxPaymentConnector` re-reads `service_components` (`component_key='PAYMENT_CONNECTOR'`, a new seed row in `db/runtime.ts` mirroring `component-itas`'s exact `REQUIRES_AUTHORITY_CONTRACT`/`DISABLED` shape) on *every single mutating call*, never a cached or constructor-time flag, and refuses with `PaymentIntegrationUnavailableError` unless it reads back exactly `SANDBOX_CONFIGURED`/`SANDBOX_ACTIVE`. This is the first genuine runtime *enforcement* use of `service_components` anywhere in this codebase — every existing read of that table (`lib/data/platform-repository.ts`) is display-only, confirmed by a targeted grep before writing this guard. Nothing anywhere writes to that row: no command, no route, no admin action exists that could ever flip it, so the guard's refusal is structural, not a policy choice a future change could silently loosen. On the (today, always-taken) refusal path, `recordRefundPayment`/`allocateRefundPayment` still record an honest `*_ATTEMPTED`/`AWAITING_AUTHORITY` audit entry rather than a bare 5xx or a silently swallowed failure — the identical fail-closed shape `verifyTaxpayerIdentifiers` already established for ITAS (`lib/data/identity-repository.ts`).
- [x] Proven in `tests/routes/module-9-payment-connector.test.ts`, deliberately split into two halves so the guarantee and the mock logic are never conflated: the REAL command path (every test but the last, all through the actual `app/api/v1/refunds/...`/`app/api/v1/payments/...` routes) shows `RecordPayment` on a genuine `PAYMENT_PENDING` claim — including three repeated retries — always refused with `AWAITING_AUTHORITY` and asserts `SELECT COUNT(*) FROM payment_instructions` stays `0` throughout, plus the wrong-status conflict, a validation failure, a permission denial, `AllocatePayment`'s conflict with no instruction to allocate against, and `GetOutstanding` correctly listing the still-unpaid claim and the connector's honest `REQUIRES_AUTHORITY_CONTRACT` state. A single, clearly-labelled `SIMULATION ONLY` test at the end directly flips `service_components` in the fake D1 — something no real command anywhere can do — purely to prove `SandboxPaymentConnector`'s mock logic (deterministic reference, `INITIATED`→`SETTLED`) is sound if it were ever hypothetically authorised, then restores the row to its real disabled default before the suite ends.

**Watch-outs:**
- This is the single most dangerous module for an accidental "just make it work end-to-end" shortcut — treat Phase D's environment guard as mandatory, not optional polish.
- Freeze-on-claim must be genuinely immutable; verify with a test that mutates the source return/invoice after freezing and asserts the claim snapshot is unaffected.

**Definition of done:** a refund claim can be validated, risk-scored, reviewed, and maker-checker approved, arriving cleanly at `PaymentPending` against a mock connector — with a hard, tested guarantee that no code path reaches a real payment instruction while Payment remains `DISABLED PENDING AUTHORITY`.

### Phase A — Generic connector model (M) — DONE 2026-08-27
- [x] `Integration` aggregate (`integration_connections`) and `SyncRecord` (`sync_jobs`) — both pre-existing tables that a full-repo grep found had zero write paths anywhere in this codebase before this phase, despite the matrix's prior "VERIFIED FOUNDATION" claim for domain #25; every row in either table was seed-only. `RegisterIntegration` (`POST /api/v1/integrations`), `ApproveIntegration`/`SuspendIntegration` (`POST /api/v1/integrations/:id/approval`, `.../suspension`) and `StartSync`/`GetHealth` (`POST .../sync`, `GET .../health`) now exist (`lib/data/integration-repository.ts`), gated on `integrations:manage`/`integrations:read`. Deliberately provider-agnostic: the same command shape registers a SaaS/ERP connection or, in principle, a government one — no ITAS-specific field anywhere. `Connector` is treated as the connection row's own config, not a separate table (the schema never separated them); `Webhook` is deliberately left to Phase D, since `webhook_subscriptions` is keyed on `api_client_id` (Developer Platform), not `integration_connections` — Phase A's own data anchor list groups `Webhook` alongside `Integration`/`Connector`/`SyncRecord` but names no verb for it, so nothing here invents one.
- [x] A real `DRAFT → CONFIGURED ⇄ SUSPENDED` state machine (`lib/domain/integration.ts`'s `INTEGRATION_TRANSITIONS`, mirroring every other module's adjacency-map pattern) drives `configuration_status`/`operational_status` together — deliberately one derived pair, not two independently-settable fields. The four pre-seeded platform connections (`ITAS`/`BIPA`/`bank-org1`/`treasury`, `db/runtime.ts`) carry free-text `REQUIRES_*_CONTRACT` values that fall entirely outside this closed three-value enum, so `assertIntegrationTransition` naturally refuses any action against them — and `RegisterIntegration` itself refuses to create a second row for a `provider_key` that already exists in the same scope, so there is no path for this phase's commands to ever register a duplicate that could then be approved in their place. Ownership is symmetric and simple: a tenant actor (`taxpayerId` set) may only register/approve/suspend/sync their own organisation's connection; an actor with no `taxpayerId` at all — a national NamRA role or a platform-technical one (`SUPER_ADMIN`/`INFRASTRUCTURE_ADMIN`, neither in `isNationalScope`'s own role list) — registers and manages platform-wide connections (`organisation_id` NULL) only; neither side can reach into the other's row.
- [x] `StartSync` is honest about this pilot's real capability: no live per-provider connector implementation exists for any provider (that is out of scope for a *generic* connector model — it is the per-provider work the matrix's own "Required closure" column for domain #25 names). Every `StartSync` call against an approved, `CONFIGURED` connection completes immediately as a `FAILED` `sync_jobs` row with a typed `last_error` reason, never a fabricated `COMPLETED` with invented record counts — the same "never claim a result nothing actually produced" posture Module 9 Phase B's `NOT_CONFIGURED` checks and Module 9 Phase D's `AWAITING_AUTHORITY` payment outcome already established. `GetHealth` reads back the connection's own stored status plus its 10 most recent sync attempts — a real projection of recorded state, not a live probe (there is nothing to live-probe). Connection discovery/listing is deliberately not duplicated here — the pre-existing `GET /api/v1/platform` snapshot's own `integrations` array already covers it.
- [x] Proven in `tests/routes/module-10-integration-connector.test.ts` (18 tests): tenant and platform-wide registration and their ownership boundaries in both directions; a duplicate registration conflict; registering `itas` again is refused for the exact same reason that protects the seeded row from ever being approved; validation and permission-denial edges; `StartSync` refused before approval and again once suspended, and honestly `FAILED` once approved; `GetHealth`'s recent-attempts projection; `SuspendIntegration` requiring a reason and refusing a second suspend; `ApproveIntegration` reactivating a suspended connection; and idempotency under a repeated key.

## The commissioning workstream (runs in parallel, not engineering)

Modules 1–10 make the system *buildable*. They do not make it *commissionable*. That is gated by a separate, non-engineering workstream someone needs to own explicitly:

- **Approval Gate sign-off** (`08-enterprise-architecture/29-architecture-approval-gate.md`): 14 named authorities, currently all blank. Assign an owner to actively pursue each signature — this doesn't happen passively.
- **Production-readiness evidence backlog** (`06-delivery/phase0-production-readiness-evidence-backlog.md`, PR-001–013): 0 of 13 closed. Each already has a named accountable owner and required approver column — use it.
- **Sequential remediation programme** (`09-assessments/CURRENT STATE ASSESSMENT.md`): Issues 1–4 are `BLOCKED — external dependency`; Issues 5–27 are `LOCKED`. Engineering work on Modules 1–10 will not unblock these — they need NamRA/ITAS/legal/security-authority engagement.
- **Keep the two workstreams visibly separate.** A module reaching "Definition of Done" here means it's engineered and tested — it does not mean it's authorised for production. Never let a passing test suite get represented as commissioning progress; that conflation is precisely what the `09-assessments/` audits exist to catch.

## Suggested cadence

- Treat each **phase** (not the whole module) as your sprint-sized unit of work — a module's total size is roughly the sum of its phase sizes (S/M/L), so a module with four M phases is a bigger commitment than one with two S phases and an M.
- Keep exactly one module "primary focus" at a time, but let Module 8 (Platform/Security/Workflow) and the commissioning workstream run continuously underneath whichever module is primary — they're cross-cutting, not sequential.
- After each phase, re-check `ARCHITECTURE_IMPLEMENTATION_MATRIX.md` and update it if the module's real status changed. If a module's status doesn't match this playbook's Definition of Done, fix the gap before declaring it complete and moving to the next module — this repo's own history shows what happens when status drifts ahead of evidence.
